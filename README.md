# نظام حجز مواعيد ورشة السيارات

واجهة عربية RTL لعرض خدمات الورشة وإرسال طلبات الحجز، مع لوحة إدارة محمية عبر Supabase Auth وRLS.

## الملفات

- `index.html`: صفحات الموقع والنماذج.
- `style.css`: تنسيقات الواجهة الأصلية.
- `app.js`: التحقق من المدخلات، الاتصال بـ Supabase، الحجز، تسجيل الدخول وإدارة الحجوزات.
- `supabase.sql`: الجداول والعلاقات والفهارس ودوال RPC وسياسات RLS.
- `README.md`: الإعداد والتشغيل.

## إعداد Supabase

1. افتح مشروع Supabase الصحيح: `https://xrwatehjxfqjiucwxyom.supabase.co`.
2. من **SQL Editor** شغّل الملف `supabase.sql` كاملًا.
3. تأكد أن ظهرت الجداول `services`, `customers`, `cars`, `bookings`, `profiles`، وأن جدول `services` يحتوي الخدمات الأولية.
4. الملف ينشئ ملفات profiles للعملاء افتراضيًا. لا يمنح بيانات التسجيل أو المستخدم نفسه دور المسؤول.
5. المفتاح الموجود في أعلى `app.js` هو مفتاح Supabase المنشور `sb_publishable_...`، وهو المفتاح المناسب للواجهة الأمامية. لا تضع `service_role` أو `sb_secret_...` في ملفات الموقع.

إذا ظهر الخطأ `42P17` عند قراءة الخدمات، حدّث سياسة `profiles` من **SQL Editor** بهذا الإصلاح، ثم أعد تحميل الموقع. السياسة الذاتية لا تستدعي `is_admin()` من داخل `profiles`، وهذا يمنع التكرار:

```sql
begin;
drop policy if exists profiles_read_self_or_admin on public.profiles;
drop policy if exists profiles_read_self on public.profiles;
create policy profiles_read_self
  on public.profiles for select to authenticated
  using (id = (select auth.uid()));
commit;
```

إذا لم يعمل المفتاح، افتح **Project Settings → API Keys** أو نافذة **Connect** في لوحة Supabase، وانسخ **Publishable key** الخاصة بالمشروع. سيبدأ المفتاح الصحيح بـ `sb_publishable_`. لا تستخدم المفتاح السري. توثيق Supabase الحالي يوضح أن publishable key مخصص للتطبيقات التي تعمل في المتصفح وأن سياسة RLS تحدد ما يمكنه الوصول إليه.

### إنشاء حساب المسؤول

لا توجد كلمة مرور افتراضية في المشروع. أنشئ مستخدمًا واختر كلمة مروره بنفسك؛ لا تُخزّن كلمة المرور في ملفات الموقع.

1. من **Authentication → Users** أنشئ مستخدمًا ببريد وكلمة مرور.
2. من **SQL Editor** غيّر البريد في الاستعلام التالي إلى بريد المستخدم نفسه ثم شغّله:

```sql
update public.profiles as p
set role = 'admin',
    updated_at = now()
from auth.users as u
where u.id = p.id
  and lower(u.email) = lower('admin@example.com');
```

3. تحقق أن الاستعلام حدّث صفًا واحدًا، ثم سجّل الدخول من زر **لوحة الإدارة**. إن لم يوجد ملف للمستخدم، أعد تشغيل استعلام مزامنة المستخدمين من `supabase.sql` ثم نفّذ الترقية.

لا تغيّر الدور من المتصفح؛ جدول profiles لا يمنح المستخدم صلاحية INSERT أو UPDATE، وسياسة RLS لا تسمح له بترقية نفسه.

## إعداد الاستضافة الثابتة

- اختر إطار العمل **Other / None**.
- اترك أمر البناء فارغًا ومجلد النشر على جذر المستودع (`.`).
- لا تحتاج إلى إضافة متغيرات بيئة للاستضافة. هذا الموقع ثابت ويقرأ رابط المشروع والمفتاح المنشور من أعلى `app.js` مباشرة.
- إذا غيّرت مشروع Supabase، حدّث `SUPABASE_URL` و`SUPABASE_PUBLISHABLE_KEY` في `app.js` ثم أعد النشر. لا تستخدم مفتاح `service_role` أو `sb_secret_...`.

تظهر خيارات الخدمة من الصفوف النشطة في جدول `services`. لقائمة الاختيار يحتاج التطبيق إلى `id`, `name_ar`, `description_ar`, و`active`، ويحتاج الحجز أيضًا إلى `slug` و`duration_minutes`. أضف صفوفًا للخدمات واجعل `active = true`. ملف `supabase.sql` ينشئ هذا الجدول مع بقية المخطط ويضيف أربع خدمات أولية؛ إنشاء جدول الخدمات وحده لا يكفي لحفظ الحجوزات، إذ يحتاج الحجز أيضًا إلى الجداول الأخرى ودالة `create_public_booking` وسياسات الأمان.

## التشغيل

يمكن فتح `index.html` عبر خادم ملفات محلي بدلًا من فتحه مباشرة:

```powershell
python -m http.server 8000
```

افتح بعدها `http://localhost:8000` من مجلد المشروع. يحتاج الموقع اتصال إنترنت لتحميل Supabase JS وTailwind وخط Cairo من CDN. انشر الملفات الخمسة معًا على استضافة مواقع ثابتة عند تجهيز الإنتاج.

## سلوك قاعدة البيانات والحماية

- الزائر يستطيع قراءة الخدمات النشطة فقط واستدعاء `create_public_booking` لإنشاء حجز.
- لا يملك الزائر أو المستخدم المسجل العادي صلاحية قراءة `customers`, `cars`, أو `bookings` أو تعديلها من REST API.
- دالة الحجز تتحقق من الاسم والجوال السعودي والخدمة النشطة والموعد المستقبلي، ثم تحفظ العميل والسيارة والحجز وتعيد صفًا يتضمن `reference_code` بصيغة `WR-` مع 12 رقمًا سداسيًا.
- قاعدة البيانات تقفل إنشاء الحجوزات داخل المعاملة وتتحقق من تداخل مدة الخدمة مع الحجوزات الجديدة أو المؤكدة؛ ويُرفض التداخل حتى لو وصل طلبان متزامنان.
- المسؤول فقط يستطيع قراءة الحجوزات وتغيير حالاتها. الانتقالات المسموحة: جديد ← مؤكد أو ملغي، مؤكد ← مكتمل أو ملغي.
- نجاح تحميل قائمة الخدمات لا يثبت وحده نجاح الحجز أو صلاحيات الإدارة.
- ملف SQL يستبدل سياسات RLS الموجودة على الجداول الخمسة التي يديرها هذا التطبيق. لا يحذف صفوف الجداول. إذا كانت لديك جداول سابقة بأعمدة أو أنواع مختلفة، خذ نسخة احتياطية وراجعها قبل التشغيل؛ `CREATE TABLE IF NOT EXISTS` لا يحوّل مخططًا قديمًا تلقائيًا.

## التحقق

بعد تشغيل SQL على المشروع، اختبر يدويًا:

1. ظهور الخدمات النشطة من Supabase.
2. إرسال حجز صالح والتأكد من وجوده في `bookings` مع مرجع حقيقي.
3. رفض الاسم أو الجوال الناقص/غير الصحيح والتاريخ الماضي.
4. إرسال حجز متداخل مع حجز جديد/مؤكد والتأكد من رفضه من قاعدة البيانات.
5. تسجيل الدخول بحساب المسؤول وعرض الحجوزات الفعلية.
6. البحث والتصفية حسب الحالة والخدمة، ثم تأكيد الحجز أو إكماله أو إلغاؤه.
7. تسجيل الدخول بمستخدم عادي ومحاولة قراءة `bookings` وتعديلها مباشرة من Supabase؛ يجب أن تمنعها RLS.
8. مراجعة الاتجاه العربي على شاشة ضيقة وأخرى واسعة.

لا تُسجّل رسالة نجاح للحجز إلا إذا رجعت الدالة بمرجع `WR-...` صالح. إذا لم يُرجع RPC المرجع فلن تعرض الصفحة شاشة التأكيد.
